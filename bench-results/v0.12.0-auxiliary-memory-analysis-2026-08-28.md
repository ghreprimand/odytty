# v0.12.0 auxiliary memory analysis

Capture completed 2026-08-28. This record publishes two explanatory analyses
that are deliberately outside the benchmark protocol: an idle resident-memory
composition and the post-storage-change scrollback scaling curve. Neither is
pooled with W6, and neither changes the W6 headline totals.

## Idle resident-memory composition

The final v0.12.0 measured artifact (`80b2fd2d`) and the exact Kitty, Ghostty,
and Alacritty artifacts and canonical profiles from the published W6/SE run
were launched serially on the benchmark environment. Each terminal used the
same isolated DejaVu Sans Mono face, native Wayland, the same tiled 1900x1010
window rectangle, and a 60-second settle. Two fresh launches were captured per
implementation with `scripts/memory-capture.py`.

Every record was `complete`: RSS and PSS were readable, the closed mapping
classes summed exactly to total RSS, both launches retained the same window
rectangle, no Xwayland path was used, and no unavailable-field substitution was
needed. Values below are bytes; the final row for each implementation is the
arithmetic mean of its two fresh launches.

The reference terminals each page about 88.6-89.4 MB of driver-classified
mappings, dominated by the same 87.5 MB `libLLVM.so.22.1` mapping. OdyTTY's
accelerated Vulkan path instead pages 10.8 MB of `libvulkan_intel.so`; its
complete driver class averages 11.6 MB. This is a mapping observation, not an
estimate of application-owned GPU allocation.

The single-process RSS values are not W6 totals. W6 uses cgroup accounting for
the terminal's complete private process tree over a ten-minute measured window;
this analysis reads one terminal process after 60 seconds. The composition can
explain fixed parts of the W6 result, but it cannot replace or soften the
published W6 current and peak figures.

## Scrollback-fill scaling curve

The scaling curve was measured after the 28-byte `StoredCell` change at
revision `f55c6089`, using fixed 640x400 geometry and deterministic depths.
Reference terminals used three launches per depth. OdyTTY's 100,000-line point
uses the separately validated eight-launch sample because two independent
three-launch samples of that exact binary and fixture disagreed by 161 MB.

| implementation | depth 0 | depth 1,000 | depth 10,000 | depth 100,000 | fitted bytes/line |
| --- | ---: | ---: | ---: | ---: | ---: |
| OdyTTY | 67.3 MB | 71.3 MB | 94.9 MB | 451.0 MB (n=8) | 3,956.5 |
| Kitty | 201.8 MB | 205.5 MB | 243.5 MB | 401.3 MB | 1,979.6 |
| Ghostty | 232.7 MB | 236.4 MB | 255.9 MB | 390.9 MB | 1,592.8 |
| Alacritty | 164.6 MB | 176.9 MB | 281.2 MB | 692.5 MB | 5,281.1 |

OdyTTY's fitted slope fell from 5,775.9 to 3,956.5 bytes per line. Its ratio to
Kitty narrowed from 2.91x to 2.00x and its ratio to Ghostty from 3.66x to 2.48x.
At 100,000 lines OdyTTY is 1.12x Kitty and 1.15x Ghostty, while remaining below
Alacritty. The OdyTTY point has substantial launch variance: the approximate
95% interval is 407-495 MB, so the absolute result is near parity with Kitty at
that depth rather than a clean win.

This curve measures resident cost against deterministic scrollback depth. The
SE retention capture measures before/burst/settled change around one workload.
Together they narrow the memory question, but neither measures time-based creep
through a long interactive session. That remains the explicitly deferred W7
workload.
