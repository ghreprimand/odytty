## 2026-10-02 -- Release v0.15.8 -- macOS idle CPU fix

Version 0.15.8 is a patch release from the `release/0.15.8` branch of
v0.15.7. The v0.16.0 development tree is not part of it.

On macOS, an untouched window's idle CPU returns to about zero. The cause
was a per-tick clone of the event-loop proxy inside `about_to_wait`, which
re-woke the macOS run loop. The clone has been present since v0.15.0. The
tick path no longer clones the proxy. On Linux and Windows, proxy clones
are cheap and showed no spin. The per-tick clone is removed there too. This
release makes no idle-CPU claim for those platforms, and no
rendering-throughput, startup, or memory claim. The v0.12.0 results remain
the applicable comparative evidence.

Publication checks for tag v0.15.8: SHA256SUMS verified for all 15 files,
and the seven always-latest aliases match their version-pinned copies byte
for byte. The minisign signature verifies with the key in `docs/install.md`.
Attestations verify for the AppImage, the Windows zip, and the macOS zip.
The Scoop manifest on master is v0.15.8. The Homebrew cask 0.15.8 sha256
`da0e88211b78f54eda1a5354f054e6c53e3f67cb00f38edc90c541cf711a71ea` matches
the macOS zip. The Homebrew formula sha256

## 2026-10-02 -- Secure keyboard input on macOS

- **Toggle Secure Keyboard Input** (palette) and the **Secure keyboard
  input** settings row (`secure_keyboard_input`, off by default) set one
  process-wide wish on macOS. `EnableSecureEventInput` runs only while the
  wish is on and an OdyTTY window has keyboard focus; a process counter
  pairs it with `DisableSecureEventInput` when focus leaves every window,
  the last window closes, the wish is turned off from any window, or the
  process exits. There is no default chord and no password-prompt
  detection.
- Chosen: hold the primitive only while focused, as Terminal.app does,
  because while it is enabled macOS withholds keystrokes from every
  keyboard-intercept tool (event taps such as text expanders, and some
  accessibility and automation tools), even when OdyTTY is in the
  background. Other apps still receive keys. A crash while it is enabled
  can leave secure input reported as active until logout.
- Each holding window shows a `SECURE INPUT` label, part of the frame
  cache signature; the label blanks the spacer of a wide glyph it cuts.
  Windows and Linux have no equivalent primitive: the row and the palette
  action are absent and a config value is kept but not applied.
- Gate: fmt, Linux plus Windows and macOS cross-target clippy,
  single-threaded tests (library 5707 passed, 0 failed, 16 ignored), file
  and doc guards, and RustSec all passed on the parent commit; the change
  applies to the current tree with only line offsets moved. macOS hands-on

## 2026-10-02 -- macOS idle busy loop in the event loop

- Device testing on an Apple M4 Mac found an untouched OdyTTY window using
  a full CPU core from launch, and the installed v0.15.7 app showed the same.
  A stack sample put the main thread in the event loop's idle hook, inside
  `EventLoopProxy::clone`. In winit 0.30 on macOS, cloning a proxy adds a
  run-loop source and wakes the run loop. The local automation service
  cloned its proxy on every idle tick, even with automation disabled (the
  default), so each tick scheduled the next one. The code has been present
  since v0.15.0.
- The automation reconcile now takes a factory for its wake callback and
  builds it, with its proxy clone, only when an endpoint actually starts.
  Every host proxy clone goes through one helper; the remaining clones are
  one-shot (shortcut registration, Wayland file-drop listener) or
  event-driven. A test runs 32 idle ticks and requires zero proxy clones; it
  fails before the change (32 clones). Linux and Windows proxy clones are
  cheap and showed no spin, but the per-tick clone is removed there too.
- No performance claim beyond the macOS idle check. Gate: fmt, Linux plus
  Windows and macOS cross-target clippy, single-threaded tests (library 5700
  passed, 0 failed, 16 ignored), file and doc guards, and RustSec all
  passed. macOS before/after idle check on the same machine is pending.

## 2026-10-02 -- Broadcast fan-out diagnostics

- Device testing found a pane created by a split inside a broadcast group
  showing `BROADCAST 2` while a typed character reached only that pane. The
  same sequence driven through the App key path delivers to every receiver,
  so the difference is not yet attributed.
- Under the existing `ODYTTY_KEY_EVENT_DIAGNOSTICS` gate, every input,
  IME commit, or paste that reaches broadcast fan-out now records one
  `broadcast-fanout` line: payload kind and byte count, the focused pane's
  numeric token, and each receiver's token with its outcome (`delivered`,
  `skipped-focused`, `skipped-read-only`, `skipped-unresolved`,
  `queued-other-window`, `write-failed`, `refused-too-large`, or `pruned`).
  An empty set logs `receivers=0`; no line at all means the input never
  reached fan-out. Typed bytes, text, titles, and paths are never recorded,
  and nothing is logged while the gate is off. Broadcast behavior is
  unchanged.

## 2026-10-02 -- Stacked and floating pane layouts

- A tab keeps its split tree as the single record of which panes exist and
  adds an arrangement beside it: tiled (the default, and the only mode older
  layouts know), stacked, or floating. **Stack Panes**, **Float Panes**, and
  **Tile Panes** are palette actions; no default chord was added. Switching
  mode never restarts a pane, and Tile returns the exact tiled geometry
  because the tree is never discarded.
- Stacked shows the focused pane over the whole content area while the other
  panes keep running at their tiled size. Floating panes are whole-cell
  rectangles with a z-order, a frame, an 8 x 2 cell minimum, and a clamp at
  resolution time, so a smaller window never deletes a pane. The focused pane
  is always painted on top; focus cycling stays in stable tree order so every
  pane is reachable, and **Focus Pane k of n** palette rows list them.
- **Arrange Floating Pane** moves (arrows) and resizes (Shift+arrows) the
  focused floating pane from the keyboard. Overlapping panes are cut around
  the panes painted above them for backgrounds, glyphs, and overlays. Known
  limits: pointer drag of a floating frame is not implemented, and a covered
  floating pane draws no inline images until it is uncovered.
- Persistence writes an `arrangement` object only for non-tiled tabs, so
  tiled layout files are byte-identical. Malformed or partial entries load
  tiled or as an unplaced pane, never as a partial rectangle; restore is
  deterministic. A pane moved from another window joins the destination tab
  as a floating pane only when that tab is floating.
- New feature, no performance claim. Gate: fmt, Linux plus Windows and macOS
  cross-target clippy, single-threaded tests (library 5695 passed, 0 failed,
  16 ignored), file and doc guards, and RustSec all passed. Device acceptance
  on Linux, macOS, and Windows is pending.

## 2026-10-01 -- New Window chord letter and sibling hold release

- Windows device testing at 49244543 still showed the `n` of
  `Ctrl+Shift+N` in the new window's prompt, removed about five seconds
  later. Two causes. First, the new window already has focus when the
  key-up arrives, so the bare press that follows it was encoded as
  ordinary typing; a modifier press and a one-character IME commit after a
  same-letter pre-edit also escaped the latch. A window that inherits the
  latch now drops its first bare press of that letter whether it arrives
  before or after the key-up, keeps the latch across modifier presses, and
  swallows that IME commit. The window that handled the chord still treats
  a press after its key-up as typing, and a different character ends the
  latch.
- Second, the new window's surface was created before the window was
  registered with the host, so the creation resize was dropped and the held
  ConPTY shell waited for the five-second fallback. The window is now
  registered first, and surface creation applies the window's current
  non-zero size, so the held shell starts on the window's grid. A 0x0
  (minimized) window still waits for the fallback, which remains.
- Bound: each new window drops at most one press of the chord letter. Linux
  and macOS have no ConPTY hold. Gate: fmt, Linux plus Windows and macOS
  cross-target clippy, single-threaded tests (library 5637 passed, 0
  failed, 16 ignored), file and doc guards, and RustSec all passed. Windows
  hands-on retest is pending.

## 2026-10-01 -- Ambiguous character width preference

- `ambiguous_width` (`ODYTTY_AMBIGUOUS_WIDTH`, profile `appearance.ambiguous_width`)
  chooses how East Asian Ambiguous characters are measured: `narrow` (the
  default, today's width table, one column) or `wide` (two columns, using
  the width crate's East Asian context table). A pane follows the profile
  that launched it; a missing profile value uses the global setting.
- Changing the value reflows that pane's primary grid and scrollback in
  place through the existing resize path. The PTY is not resized and the
  shell is not told, so a prompt drawn under the old width stays as drawn
  until the shell repaints it; a selection or search hit can land on
  different cells after the remeasure. An active alternate screen is left
  for the application to repaint. Width policy is part of the projection
  cache key, so a same-width policy change never reuses old row counts.
- Overlay chrome, the tab bar, the search status line, and the glyph atlas
  stay on the narrow table: a shared atlas cannot cache two slot widths for
  one codepoint while two panes disagree, and the grid's continuation cell
  reserves the second column. IME pre-edit follows the pane's policy.
- Verification: fmt, Linux plus Windows/macOS cross-target clippy,
  single-threaded `cargo test` (5610 library tests passed, 16 ignored), the
  guards, and both RustSec audits pass; width conformance and the new
  ambiguous-width tests cover both tables and the reflow. Hands-on Linux
  acceptance is pending.

## 2026-10-01 -- Move tabs and panes between windows

- A tab or a pane can move to another window of the same process, or into a
  window of its own, from the command palette: Move Tab to New Window, Move
  Tab to Window..., Move Pane to New Window, Move Pane to Window.... The "to
  Window..." rows reuse the merge picker: each other window shows a numeral
  and "Press N to move here". Rows appear only when they can work (a sibling
  window exists, something stays behind, the tab is split).
- The moved shell keeps running. Its PTY or attached session, writer, pump,
  terminal model, scrollback, images, selection, search, recorder, profile
  binding, and `--hold` state move as owned values between the two workspace
  arenas; nothing is respawned, detached, or replayed. A moved tab keeps its
  panes and layout; a moved pane becomes the only pane of a new tab whose
  identity is minted from the destination's token range, and the pane it
  leaves behind takes over its split.
- The move is a transaction: a preflight checks token collisions and
  capacity without mutating either window; a refused destination or a new
  window that cannot open restores the tab index, workspace, pane tree,
  focus, and zoom exactly, with a notice. Before a pane leaves, the source
  settles the state that names it (focus-out report, pending paste and image
  confirmations, IME composition, context-menu target, open overlay, drags)
  and afterwards prunes OSC 52 consents and reflows. The destination drops
  its presentation caches, parks timers, applies its presentation policy,
  activates the tab, and reflows.
- Moving a window's last tab retires that window, and the primary autosave
  role moves to the destination. The quick terminal neither sends nor
  receives. Attached host-session ids are shared across windows, so a session
  attached in another window is refused with a notice rather than attached
  twice.
- Drag tear-out is not supported: on Wayland the compositor owns placement
  and winit reports no cross-window drag, so the palette is the route there
  and on every other platform.
- Chosen, and reversible: palette rows only (no context-menu rows yet); a
  window's only tab does not move to a new window; a moved pane keeps its own
  recorder state; an open command-export save dialog stays with the window
  that opened it while the export follows the pane.
- Verification: fmt, Linux plus Windows/macOS cross-target clippy,
  single-threaded `cargo test` (5617 library tests passed, 0 failed), the
  guards, and both RustSec audits pass; 5 model tests and 9 host/App tests
  cover the picker move, last-tab retire with primary handoff, pane to a new
  window with hold, IME, and focus-out, exact restore when the new window
  cannot open, only-tab and quick-terminal refusals, cross-window attach
  dedup, and the palette rows. Hands-on acceptance on Linux (including NVIDIA
  window create and destroy), macOS, and Windows is pending.
