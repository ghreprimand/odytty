# v0.10.0 Baseline

Reproducible starting point for the v0.10.0 release-hardening program. Every
figure below was measured at one revision with the commands printed beside it,
and successful checks are kept distinct from ignored tests, runtime skips,
platform exclusions, and unmeasured surfaces.

This is a fresh capture, not an edit of `docs/stabilization-baseline.md`. That
document remains the record of the pre-1.0 stabilization capture taken at an
earlier revision; where the two disagree, the difference is work that landed in
between and is called out here.

Nothing in this document authorizes a `v1.0` tag. The target is `v0.10.0`.

## Production-bearing and test-only classification

The size rule applies to Rust source a normal build compiles, so "normal build
compiles it" has to be decided by evidence. Classifying by filename would let a
file named for tests carry product code that no gate then measures.

`scripts/production-file-guard.py` walks the real module graph. The roots are
the crate's non-test targets (`src/lib.rs`, `src/main.rs`, and any
`src/bin/*.rs`); each `mod name;` declaration is an edge resolved with Rust's
own rules including `#[path = "..."]`; an edge is test-gated when its `cfg`
predicate can hold with `test` set and cannot hold with `test` clear. A file is
production-bearing when some root reaches it along a path with no test-gated
edge.

```
python3 scripts/production-file-guard.py --json
```

| Quantity | Value |
| --- | ---: |
| Tracked `src/**/*.rs` files | 351 |
| Production-bearing | 225 files, 160,723 physical lines |
| Test-only | 126 files, 70,819 physical lines |
| Unclassified | 0 |
| Module edges | 349 (42 test-gated) |
| Audited exclusions | 0 |

### Corroboration against the compiler

The classification was checked against what `rustc` actually reads, using the
dependency-info files a build emits:

```
cargo build --locked                 # target/debug/odytty.d, target/debug/libodytty.d
cargo test --locked --lib --no-run   # target/debug/deps/odytty-<hash>.d
```

| Check | Result |
| --- | --- |
| Files the normal Linux build reads under `src/` | 223 |
| Of those, any classified test-only | 0 |
| Production-bearing files absent from the Linux build | 2 |
| Test-only files absent from the `cfg(test)` build | 0 |

The two production-bearing files the Linux build does not read are
`src/pty/windows.rs` (`#[cfg(windows)]`) and `src/native/macos_open_with.rs`
(`#[cfg(target_os = "macos")]`). Both are product code on a shipped platform
and are correctly subject to the rule. Three further files are absent from the
`cfg(test)` library build for equally specific reasons: `src/main.rs` and
`src/cli.rs` belong to the binary target, and `src/native/app/image_paste.rs`
is declared `#[cfg(not(test))]`.

Every test-only file is compiled under `cfg(test)`, so "test-only" here means
"compiled only for tests", never "dead".

The classifier's first cut disagreed with the compiler on one file, and the
disagreement was the reason to run this check rather than assert the result.
`src/native/test_support.rs` is declared
`#[cfg(test)] pub(in crate::native) mod test_support;`, and a scanner that
tracked "attributes seen most recently" discarded the gate when it met the
visibility qualifier, classifying a test-only module as product code. The
scanner now derives attributes from the whole item slab and rejects any prefix
it does not recognize, so the failure mode is an error rather than a silent
misclassification.

## The size guard

`scripts/production-file-guard.py` enforces a maximum of 1,999 physical lines
for every production-bearing file. It runs as its own blocking CI job and is
part of the pre-commit gate in `CONTRIBUTING.md`. It is offline, needs no
toolchain, and uses the standard library only.

It fails closed in every direction that could understate the problem: a tracked
`src/**/*.rs` file no root reaches is an error rather than an assumed-dead
exclusion; a `mod` declaration that resolves to no file or to two files is an
error; a `cfg` predicate the program does not model resolves to "may hold in a
normal build"; a source-level `include!` is an error because it would add edges
the module walk cannot see; and an exclusion entry that no longer matches a
tracked file is an error so the exclusion table cannot rot into a blanket
permission. The exclusion table is empty: `src/` currently holds no generated,
vendored, fixture, or data-only Rust.

Because the rule is introduced against a tree that already breaks it, the guard
has two modes.

```
python3 scripts/production-file-guard.py                                    # the rule, nothing forgiven
python3 scripts/production-file-guard.py --baseline scripts/production-file-baseline.tsv
```

The second is what CI runs. It is a ratchet, not an amnesty. It fails when a
file not in the list goes over the limit, when a listed file grows past its
recorded size, when a listed entry names something that is not a tracked
production-bearing file, and when a listed file comes back under the limit
without its entry being removed. The list can therefore only shrink, and when
it is empty the flag has nothing left to forgive.

The guard's own fixtures run first in the same CI job
(`python3 scripts/production-file-guard.py --self-test`), because a defect in
the module walk would quietly stop measuring product code, which is the exact
failure the rule exists to prevent. The self-tests cover classification of
plain, gated, `any(test, ...)`, `not(test)`, feature-gated, `#[path]`,
visibility-qualified, and doubly-declared modules; the boundary at exactly
1,999 and 2,000 lines; unreachable, unresolvable, ambiguous, nested, and
`include!`-bearing sources; and all four states a backlog entry can be in.
`scripts/coverage-surfaces.py --self-test` runs in the same job because the
guard imports its `cfg` evaluator rather than keeping a second copy.

## Rerun procedure

From a clean checkout of the recorded revision:

```
git rev-parse HEAD                       # a136209fb16a177708ea4ddc995ba2cb3c70f5a8
git status --porcelain                   # empty

cargo fmt --check
cargo clippy --all-targets --all-features --locked -- -D warnings
cargo test --locked
bash .github/scripts/rustsec-audit.sh

python3 scripts/production-file-guard.py --self-test
python3 scripts/production-file-guard.py --json
python3 scripts/production-file-guard.py --baseline scripts/production-file-baseline.tsv
```

Run the gate commands one at a time under an explicit memory and CPU bound.
Record ignored, skipped, unsupported, unmeasured, and unavailable-hardware
outcomes as themselves; none of them is a pass.
