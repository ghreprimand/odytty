# v0.15.0 ownership and platform contracts

Development scope: quick terminal, owner-scoped structural automation, external
file drop, and keyboard-first window merge. This document records implementation
constraints; it does not claim runtime or release acceptance.

## Window and session ownership

The v0.14.0 baseline has one `native::app::App` per process. New Window launches
another process. Each `WorkspaceSet` owns a flat `SessionToken` arena; its
workspace and tab trees refer to those sessions. `SessionSource` owns a local
PTY or a Unix attach client. Pumps retain the terminal, writer, session token,
and event-loop proxy. Moving a layout alone cannot move that ownership.

The v0.15.0 transfer boundary is one process. A process-level window owner routes
native window events to existing `App` instances. New Window creates a sibling
window under that owner. Sessions remain in the existing `WorkspaceSet` arenas;
no parallel terminal registry or snapshot replay is introduced. Session, window,
tab, and workspace identifiers must remain unique and non-reused during the
process lifetime, including when a workspace's first pane closes.

Merge and Pull use the same transaction. Preflight resolves stable source and
destination identities, rejects stale or closing windows and conflicting modal
operations, validates every pane token, and reserves destination capacity before
changing either owner. Commit moves complete source workspaces in order,
preserving their tabs, pane trees, active selections, bindings, PTYs, profiles,
attach clients, and replay state. It does not detach, respawn, replay output, or
reparent native surfaces. Queued session events resolve the new owner. Source
window teardown follows successful commit and must not close transferred PTYs.
Failure before commit leaves both windows unchanged. Concurrent closure is
serialized at the event-loop boundary; process crashes retain the existing
local-versus-detached session survival distinction.

The palette and Session Navigator offer "Merge This Window Into..." and
"Pull Window Into This One...". A keyboard picker assigns temporary numerals to stable
targets and each candidate paints its numeral inside its own surface. Closing
or cancelling the picker removes all labels. Metadata is bounded and escaped.
Independent process instances cannot transfer local PTYs and are explicitly
unsupported targets. The same ownership primitive supports future v0.16.0
tear-out; tear-out is outside this release.

The current implementation connects `MultiWindowHost` to the native event loop
and routes both palette commands and Session Navigator actions to one merge
picker. In an empty Navigator query, `i` requests merge and `p` requests pull
when a sibling window exists; otherwise those keys remain filter input.
Candidate numerals are painted in the rendered grid snapshot, independently
of native window decorations. Window token ranges refuse allocation at
exhaustion instead of reusing an identity. Focused ownership, transaction,
picker, overlay, and Navigator tests cover these seams. Live second-window
creation, numeral visibility, transfer, startup readiness, and independent
Wayland, X11, macOS, and Windows acceptance remain unverified.

## Quick-terminal role

One dedicated quick window per owner has a distinct identity and profile. It is
created on explicit summon, retains its sessions while hidden, and repeated
summons serialize through one lifecycle state. A creation reservation closes the
interval before the native window identity is attached, so rapid summons cannot
start a second factory request. Ordinary restore snapshots explicitly exclude
the quick identity, including clean-exit writes after ordinary-window closure.
Closing or merging away the quick window clears the reservation and identity so
one later summon can recreate it. Hidden state does not imply that local PTYs
survive a process crash; restart restores only the last ordinary snapshot and
leaves the quick terminal absent until summoned.

Quick access defaults off. Its settings cover shortcut, profile, edge, bounded
logical dimensions, monitor policy, animation, and hide-on-focus-loss. Motion
defaults off and reduced motion suppresses it; focus-loss hiding defaults off.
An open overlay, search, copy/hint/rename mode, or process merge picker retains
interaction ownership and suppresses focus-loss hiding until it releases input.
Monitor selection uses one current display snapshot: a missing fixed index falls
back to the active ordinary-window monitor, then primary/first, then a bounded
default. Geometry is recomputed before every show, so unplugging or rescaling a
monitor while hidden cannot retain an off-screen placement.

Summoning the existing window requests visibility and focus without creating a
desktop-specific copy. Linux window-manager/compositor stacking, macOS full-screen
Spaces, and Windows foreground/virtual-desktop policy may keep another surface
above it or decline desktop migration; OdyTTY never reports OS focus merely from
issuing the request. Those platform outcomes, live display reconfiguration, and
full-screen behavior remain device-only acceptance. Startup registration begins
only after some ordinary surface has presented: Linux and Windows perform the OS
grab on a worker, while macOS performs its required main-thread Carbon call after
that same readiness gate.

Linux Wayland portal/compositor adapters, X11, macOS, and Windows independently
report registration pending, confirmed, denied, conflicting, unavailable, or
lost. A requested shortcut is never reported as registered. Unsupported Wayland
environments must offer actionable compositor-binding guidance. Registration,
discovery, and retry never block the first usable ordinary local terminal. A
failed platform confirmation raises stable remediation text in the first live
terminal window and writes the same reason to the log; confirmed success raises
no failure notice.

## Local structural control

The CLI and server share a versioned, bounded, typed protocol. Requests list and
focus window/workspace/tab/pane identities, open a named profile, create a
tab/split/workspace, rename an object, and query non-sensitive capabilities and
status. There is no arbitrary input, terminal-content read, command string,
environment override, file upload, or profile-write capability. Profile opening
uses the saved profile and existing launch resolver. Terminal output cannot
authorize any request.

Unix uses an owner-private local socket with directory and peer-UID checks.
Windows uses a local-only named pipe with an explicit owner DACL, remote-client
rejection, and verified client identity. No network listener or inherited handle
exposes either endpoint. Permissions are a platform-specific test requirement;
Unix results do not establish Windows security.

Message, connection, queue, response, and rate limits apply before allocating
or dispatching. Structured errors distinguish version mismatch, unsupported
capability, invalid request, stale identity, busy, timeout, and permission denial.
Requests execute through existing event-loop actions. A timeout cannot leave an
unacknowledged queued mutation that executes later. Endpoint cleanup must never
unlink a replacement instance's endpoint. Restoration creates fresh live IDs;
detached host IDs retain their separate namespace and do not grant input access.

Tab and workspace creation identities now live on the existing model objects,
seeded once from their first newly allocated pane. They survive focus changes,
original-pane closure, tab moves, and window merge without a parallel registry.
Restoration allocates fresh objects and identities. Navigator keyboard and
context-menu routes resolve those identities against current ownership before
acting. The live automation bridge resolves the same identities against the
current `App` owners; it does not maintain a second session registry.

The current `src/automation` foundation defines version-one request and response
frames capped at 64 KiB, names capped at 256 bytes, and structural replies capped
at 1,024 objects. Replies omit titles, paths, command lines, and terminal data.
The handoff queue holds at most 32 requests, accepts at most 32 per one-second
window across callers, and dispatches at most eight per event-loop turn.
Read-only access cannot enqueue structural mutations. Abandoned or expired
queued requests are cancelled before dispatch. A request already executing when
its two-second wait expires returns `outcome_unknown`; clients must not retry a
mutation automatically. The opt-in `automation_endpoint` setting connects that
foundation to the native event loop on Linux, macOS, and Windows. It remains off
by default, so ordinary startup creates no socket, queue, entropy, or transport
thread. When enabled, the host binds only after a terminal frame has been
presented. Linux uses `$XDG_RUNTIME_DIR/odytty/control-<pid>.sock` and refuses
when the runtime directory is unavailable; it never falls back to `/tmp`. macOS
uses an owner-private `control` directory below OdyTTY's existing state
directory. Startup removes only a dead process's stale socket after rechecking
its device and inode. Clean exit and setting disable cancel pending requests and
remove the owned endpoint without unlinking a replacement.

Windows binds `\\.\pipe\odytty-control-<pid>` with an explicit protected DACL
whose sole access entry grants the current user SID full control. The initial
`CreateNamedPipeW` call uses `FILE_FLAG_FIRST_PIPE_INSTANCE`; later instances
are created while an existing instance still owns the name. Byte-mode pipes set
`PIPE_REJECT_REMOTE_CLIENTS`, and handles are non-inheritable. The server obtains
the client PID and compares its process-token user SID before reading; the CLI
performs the symmetric server-PID SID check before writing. Both checks resolve
the peer PID to its process token, so a PID recycled between the pipe query and
the token read is a known residual; every principal other than the owner is
still refused, and impersonation-based verification remains a possible
strengthening. Eight worker slots,
32 accepted connections per second, 64 KiB framing, and absolute overlapped I/O
deadlines match the Unix bounds. Shutdown cancels work and closes all handles;
the pipe name then vanishes without filesystem cleanup.

The Windows CI leg compiles and executes same-user capability round trips,
exclusive-name collision refusal, truncated and oversized frame refusal without
an owner wake, local endpoint-name validation, and the exact remote-rejection
mode construction. Win32 does not expose the `PIPE_REJECT_REMOTE_CLIENTS`
creation bit through `GetNamedPipeInfo`, so remote-machine refusal, DACL behavior
across a second local account, timeout behavior under a stalled peer, and handle
lifecycle remain hands-on Windows checks before release.

Each automation wake dispatches at most eight requests, then schedules another
event-loop turn when work remains. List, status, focus, profile, tab, workspace,
split, and rename operations use the existing `App` actions and stable model
identities. Structural permission is rechecked at dispatch, stale or restored
identities return `stale_identity`, detached identities are not live objects,
and replies contain no terminal text, paths, titles, or command lines. Every
structural mutation honors the owning window's interactive guards: while an
overlay, search, copy mode, hint selection, rename field, or OSC 52 write
confirmation owns interaction the request returns `busy`, exactly as keyboard
input is held, so pane-specific modal state is never carried onto another pane.
A pointer-owned divider gesture is settled against its original layout at the
mutation boundary, as the keyboard ladder settles it before routing a key.
A listener thread that stops on its own (accept failure, or on Windows a failed
successor pipe instance) wakes the owner and is handled on that turn: the
runtime shuts down, the setting no longer reports a live endpoint, and a notice
asks for the setting to be toggled off and on to retry; no automatic rebind
loop exists, and disabling a faulted endpoint releases it the same way.
On Windows, a client that connects and closes before the listener observes it
consumes that pipe instance (`ConnectNamedPipe` reports `ERROR_NO_DATA`); the
listener replaces the instance and keeps accepting rather than treating it as
a fault. The name is briefly absent until the replacement exists, so the CLI
retries a missing name for at most 250 ms before reporting it. Focusing an object owned by the
hidden quick terminal returns `unavailable` rather than claiming success while
the native window stays hidden; the global shortcut remains the summon path.
Status resolves one object directly, and creation replies compare only the
previously active identity, so a client cannot force whole-tree allocations
through repeated requests. The same
setting controls endpoint availability and structural permission; there is no
separate live read-only endpoint mode. Windows follows the same opt-in and
post-first-frame lifecycle through its owner-verified named-pipe transport.

`odytty control --endpoint PATH [--json] COMMAND [ARGS]` sends one typed request
to an explicitly selected endpoint. `control --help` lists the commands and ID
syntax. Output omits names, paths and terminal data; unknown mutation outcomes
are errors and never retried automatically. Endpoint paths preserve the OS
string representation. Unsupported platforms return an unavailable result.

The Unix transport requires an existing same-owner 0700 parent directory and
checks ancestor ownership and write permissions on the parent's resolved real
path; a symlinked parent binds at the resolved directory, never through the
link. It creates a 0600 socket,
never replaces an existing endpoint, verifies same-user peer credentials on
both sides, and matches the parent/socket identities before cleanup. It bounds
acceptance to 32 connections per second and eight workers, with absolute I/O
deadlines and cancellation of pending requests when disconnects are observed.
Linux uses `SO_PEERCRED`; macOS uses `getpeereid`. Native platform execution,
hostile-client coverage and security review remain separate acceptance gates.

An independent cancellation handle lets a connection monitor cancel pending
work while its worker waits. Capability changes invalidate queued mutations by
epoch, including across disable/re-enable; dispatch rejects them before calling
the owner. Owner shutdown wakes queued callers with `unavailable` and rejects
new submissions. The future bridge must schedule another dispatch after eight
requests, and the CLI treats a lost or partial mutation response as an unknown
outcome rather than retrying a mutation. Those integration tests remain open.

## File-drop insertion

Native path events retain their supported `PathBuf` representation. Unix byte
paths must never be converted lossily; Windows paths must not silently replace
unpaired UTF-16. Unsupported representations or shell families produce an
actionable refusal. Drop events never read file contents, open a URI, upload,
change directory, append Enter, or execute a command.

The active pane's known launch-shell family selects Bash, Zsh, Fish, or
PowerShell quoting. Unknown shells, stale ownership, and remote tabs fail closed.
Untrusted terminal-authored metadata cannot select a quoting dialect. Multi-file
ordering and bounds are preserved as one explicitly accepted insertion. No local path
is silently interpreted as a remote filesystem path.

The policy is the shipped v0.13.0 implementation in
`src/native/paste_policy.rs`, `src/native/app/paste.rs`, and
`src/native/app/clipboard_routing.rs`, documented in
[Paste safety](features.md#paste-safety). Clipboard, PRIMARY, palette/menu paste,
and external text/path input must converge on that authority. Pending input is
cancelled on stale pane, relevant mode change, focus loss, or explicit Cancel.
Integrated-SSH image upload retains its separate confirm-first boundary: only a
Paste action whose clipboard has no text can offer a clipboard image for upload.
A native path drop never reads the clipboard or enters that upload route, and
remote, attached, and reconnecting panes refuse the drop as non-local before any
path is staged.

The sibling text-to-PTY routes have these boundaries:

| Route | Paste-safety preview, size, and cancellation policy |
| --- | --- |
| Clipboard, command/menu/context paste, and Linux PRIMARY | All call `route_paste_text`. Risky unbracketed text is held for preview and cancellation; bracketed paste has a 32 MiB whole-transaction cap. Plain unbracketed paste retains its documented chunked behavior without a whole-payload cap. |
| Native file path drop | Always held for explicit confirmation. The collection is capped at 128 paths and 256 KiB of path bytes, the quoted insertion at 1 MiB, and any overflow or cancellation discards the whole batch. |
| External text drop | Reserved `route_external_text_drop` calls `route_paste_text`, but there is no live platform event. If one is added, it inherits the clipboard policy rather than writing directly. |
| Local automation text | Reserved `route_automation_paste` calls `route_paste_text`, but protocol v1 deliberately exposes structural operations only and cannot send text. |
| OSC 52 clipboard-read reply | Exempt: this is a terminal-protocol reply to the requesting child, not pasted user text. It is disabled by default and requires the active pane plus observed window focus; the reply is OSC-framed and base64-encoded rather than executed as terminal input. |
| Keyboard and IME commit | Exempt: these are interactive input events, not paste transactions. Existing overlay/modal ownership gates decide whether they reach the PTY. |

`winit` `DroppedFile` events now enter the same `process_window_event` route in
both the single-window and multi-window hosts. Each `PathBuf` is accumulated as
part of a user-managed collection in a bounded preview until explicit acceptance
or cancellation; no timer or event-loop boundary is treated as an OS transaction
boundary. Overflow cancels the whole staged insertion. File insertion always
confirms, including with bracketed paste, and never offers Paste as One Line
because rewriting quoting would change path semantics. Focus loss, owner or mode
changes, and shell-classification changes cancel the pending insertion.

Unix insertion authority is checked again at confirmation. The PTY launch shell
must own the foreground process group according to `tcgetpgrp`, be the only
process in that group, and have a current executable that still classifies as
its launch-time Bash, Zsh, Fish, or PowerShell family. Linux scans one bounded
pass of `/proc/[0-9]*/stat` for process-group membership, refusing on any
directory or read error other than a vanished entry, and resolves the executable
through `/proc/<pid>/exe`. macOS obtains bounded group membership through
`proc_listpids(PROC_PGRP_ONLY, ...)` and resolves the executable with
`proc_pidpath`. Other Unix platforms refuse until they have an equivalent
membership view.

A foreground job, same-group child, in-place `exec`, missing or truncated
metadata, attached or remote pane, and unknown shell all refuse insertion. OSC
133 and all other terminal-authored output are never authority for input. The
membership observation and PTY write are not atomic, so a process can join the
group between them; that residual race matches the accepted observation boundary
of close confirmation. Deliberately renaming another executable to a supported
shell is not defended: a program already running as the user can write to that
user's terminal itself. Windows refuses file-path insertion with a notice that
names the platform, because ConPTY has no equivalent foreground-process-group
signal; launch metadata alone is insufficient.

Backend delivery still requires real-device validation on X11, Wayland, macOS,
and Windows. In particular, receiving `DroppedFile(PathBuf)` in the shared event
route does not by itself establish Wayland compositor support. This is the only
drop payload `winit` delivers to OdyTTY on those platforms; it exposes no text-
drop window event. The reserved external-text route therefore has no live
platform source in v0.15.0.

Quoting follows the shell's literal-string rules, including
[Fish byte escapes](https://fishshell.com/docs/4.0/language.html#escaping-characters)
and [PowerShell quote escaping](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_quoting_rules).
These references define token encoding; they do not establish native runtime
acceptance.

## Evidence required before release

Retained local formatting, Clippy, single-threaded tests, RustSec audit, source
and public-content guards, and blocking Ubuntu/macOS/Windows CI are required.
New user-facing behavior needs concise hands-on acceptance. Global shortcuts,
focus/fullscreen, monitor scaling, virtual desktops, file drops, and merge
numerals require separate real-device evidence. Startup readiness comparisons
must cover disabled and enabled features without discovery on the ordinary
first-terminal critical path. No v0.12.0 benchmark is relabeled as v0.15.0 data.

The informational `ttf-parser` exception still expires on **2026-10-15**.
