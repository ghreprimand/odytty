# v0.13.0 Foundation Contract

This document began as the documentation-only foundation for v0.13.0. It
records the repository surface before implementation, the architecture
decisions later work must preserve, the cross-platform acceptance target, and
the existing performance evidence that remains applicable. Implementation
status was reconciled as the phases landed. The tagged v0.13.0 release has now
passed its automated closure gates; the exact results and remaining on-device
limitations are recorded in [`release.md`](release.md).

The release target is deliberately narrow: safer non-bracketed paste,
OSC 133-backed command-output actions, and bounded completion, progress,
activity, and notification presentation. The ordinary local terminal must
remain the fastest route to a usable prompt. Later roadmap work is mentioned
only where v0.13.0 must avoid foreclosing its security or ownership boundary.

## Status vocabulary

This record uses the following terms consistently:

| Term | Meaning |
| --- | --- |
| Shipped | Present in the current runtime and documented as such. |
| Foundation | Present, but not yet wired to the planned user action. |
| Planned v0.13.0 | Historical inventory label for work that was absent when this record was frozen. |
| Decision only | A later release owns implementation; v0.13.0 freezes only the boundary. |
| Unsupported | The platform intentionally has no such surface. |
| Unmeasured | No qualifying evidence exists. This is not a pass or failure. |

## Architecture decision record

**Status:** Accepted for the v0.13.0 implementation contract.

**Decision date:** 2026-08-30.

**Scope:** These decisions constrain v0.13.0 and reserve compatible seams for
v0.14.0 through v0.20.0. They do not implement those later features.

### AD-13-01: Command ranges remain metadata over the terminal grid

OSC 133 A/B/C/D boundaries attach to logical terminal lines in the core. A
command range is derived from those marks and the live buffer generation; it is
not a second document tree and it does not own copies of command output. Reflow
moves logical anchors with their rows. Scrollback eviction invalidates any
range whose required anchor was evicted. Clear/reset and alternate-screen
transitions invalidate ranges according to the existing prompt-mark rules.
Synchronized output delays presentation only and does not create a separate
range timeline. The existing same-row D-plus-A merge retains the preceding
exit status and next prompt boundary. An offset-bearing D stamped over C on one
soft-wrapped logical line retains both explicit boundaries; a following A
retains that composite plus the next prompt boundary. Zero-offset silent
commands and any other unrepresentable ambiguous mark combination disable the
action rather than inventing a command.

Native actions receive an opaque command-range handle and resolve it again at
execution time. A missing mark, changed generation, evicted boundary, partial
transcript, or unsupported shell disables the action rather than guessing.
Each action identifies its span explicitly as output-only or prompt plus command
and output; it never infers a variant from the current selection. Selections and
exports read visible cell text through the existing plain-text projection.
Escape bytes, OSC payloads, hyperlink metadata, image payloads, and private
working-directory metadata are never part of exported text.

Terminal snapshot envelopes may preserve the prompt marks already required to
restore a detached terminal. Workspace and named-layout files remain
shape-only. No command text, output copy, or inferred history is added to them.

### AD-13-02: Profile precedence extends the single settings resolver

The future named-profile chain, from lowest to highest priority, is:

1. built-in defaults;
2. global config-file values;
3. the explicitly selected named profile;
4. startup environment variables;
5. explicit launch CLI overrides.

An unspecified profile field falls through to the global value. Environment
keys pinned at startup remain pinned during reload. Restored workspaces store a
profile name, not a materialized copy; a missing profile warns once and falls
back to global settings. Connection-specific fields remain connection data and
do not silently become a general profile. Profile enumeration and remote/WSL
discovery are cached, asynchronous, or on demand and cannot block the first
default local prompt.

v0.13.0 global notification and paste settings must use the existing resolver
and serialization/writeback seams. Per-profile overrides become active only
when the v0.14.0 profile model ships.

### AD-13-03: Paste policy observes source text before transport encoding

The risky-text predicate and escaped preview operate on the original text
returned by the clipboard, PRIMARY selection, or future text source. They run
before `encode_paste_chunks` performs the shipped plain-paste normalization of
LF, CRLF, and CR to CR. This preserves the distinction among source line-ending
forms, produces truthful line counts, and prevents normalization from hiding a
risky delimiter or control byte.

Once a paste is confirmed, the policy passes the original text to the existing
encoder. Plain paste receives exactly the existing line-ending normalization;
child-enabled bracketed paste receives exactly the existing framing and end-
marker sanitization. The policy neither pre-normalizes nor rewrites the payload.

### AD-13-04: Terminal notification requests are untrusted hints

PTY output can propose bounded progress or notification state, but it cannot
choose durable application chrome, create actions, open a URL, write a file,
send input, or bypass focus and user-policy gates. The parser produces a
sanitized data event. The owning pane/session converts it to transient in-app
state and, when policy permits, a platform adapter request.

Notification text is length-bounded plain text after control stripping. It is
never interpreted as markup, a URL, a command, or an application action. It is
not persisted by default. Output-derived desktop notifications use generic
application-owned wording by default, such as a command-completed state and a
user-assigned pane label; raw OSC text, remote identities, credential-shaped
text, and unredacted working-directory paths are not copied into OS chrome.
Rate limiting and deduplication apply per pane and at the application boundary.
A tab or workspace displays only the rollup of its owned panes, and clearing
ownership removes the rollup. Native adapter failure leaves in-app state
available and is not reported as native notification success.

BEL remains a separate input and setting. Command completion never steals
keyboard focus. Desktop notification defaults are limited to an explicit
one-shot request or a background/unfocused owner under the selected policy.

### AD-13-05: The quick terminal is an application-owned role

The v0.15.0 quick terminal will be a dedicated OdyTTY top-level window role
with its own visibility and restoration policy. The platform global-shortcut
adapter only requests summon/hide; it does not own a PTY, parse terminal data,
or select an arbitrary existing window. Losing shortcut registration leaves a
normal launch path and never prevents startup.

The quick terminal reuses the ordinary session, pane, renderer, settings, and
security models. It does not gain an elevated automation channel or implicit
shell input. Platform discovery and registration are asynchronous or explicit
and do not delay readiness of an ordinary local terminal.

### AD-13-06: Automation is local, structural, owner-scoped, and explicit

The v0.15.0 automation endpoint will use platform-native local IPC with a
same-user authorization check. It will not bind TCP, UDP, WebSocket, HTTP, or
any other network listener. Its protocol carries typed structural requests,
not shell command strings. The CLI and application share the same schema and
authorization checks.

Terminal output, OSC payloads, restored metadata, triggers, hyperlinks, and
notifications have no route to this endpoint. Read-only inspection and
structural actions are distinct capabilities. Any action that would insert
text or affect more than one pane requires an explicit user-authorized mode;
authorization is never inferred from focus or from a message appearing in the
terminal. The endpoint stores no password, token, API key, SSH credential, or
long-lived secret.

### AD-13-07: File drop is quoted text insertion, never execution

Each dropped local path is treated as untrusted input. The owning pane's known
shell family selects a tested quoting implementation. Paths are emitted as one
text-paste transaction, separated without joining them into a shell program,
and no Enter or submit key is appended. The resulting text traverses the same
risky-paste confirmation policy as clipboard and PRIMARY text.

If the active shell family is unknown or a platform/shell combination has no
correct quoting contract, direct insertion is unavailable. The UI may offer
copy-to-clipboard or cancel, but it does not guess. A drop never opens the file,
uploads it, changes directory, invokes the shell, or reads file contents.

### AD-13-08: Window movement transfers model ownership, not native surfaces

The v0.16.0 tear-out/reparenting design moves a typed tab or pane session
between OdyTTY window models. The destination creates its own render and input
surface; the implementation does not attempt to reparent a platform-native
child window or GPU surface. PTY ownership and session identity remain stable,
and terminal bytes are not replayed to reconstruct state.

Same-process movement is the first supported boundary. Cross-process movement
requires an authenticated local structural handoff and a session source that
can transfer or reattach without losing the terminal model. Until those
conditions exist, cross-process movement is unsupported rather than emulated by
closing and respawning the command.

### AD-13-09: Unicode has one canonical logical model

Terminal storage remains a logical cell grid. A grapheme cluster is indivisible
for shaping, selection endpoints, copy, hit testing, reflow, and cursor mapping.
Combining code points attach to their base cell within the existing bounds;
wide cells and their continuation cells move as one unit; malformed text uses
the existing replacement behavior. No presentation layer may invent a second
width table.

The v0.17.0 bidi and complex-script work may reorder presentation only through
a reversible logical-to-visual map shared by rendering, selection, cursor,
hit-testing, damage, and copy. PTY byte order, scrollback logical order, and
plain-text export remain logical. A platform font difference may change glyph
availability, not terminal cell width semantics.

### AD-13-10: Windows session hosting is a separate security boundary

The v0.18.0 Windows detached-session host will own ConPTY outside the window
process and use Windows-native same-user IPC. Its endpoint must have an
owner-restricting security descriptor, reject an unverifiable peer, bound every
frame before allocation, and define child/job-object and host-exit behavior
explicitly. It will not translate the Unix-domain-socket implementation or
infer security from POSIX permissions.

Windows default-terminal registration is a separate, user-controlled feature.
It never silently writes registration state and does not grant session-host
authority. Until the Windows host passes its own lifecycle, registration,
restore, and on-device gates, Windows workspaces continue to restore fresh
shells and detached sessions remain unsupported.

### AD-13-11: Command export uses a dependency-backed native save adapter

Phase C uses [`rfd::AsyncFileDialog`](https://docs.rs/rfd/latest/rfd/struct.AsyncFileDialog.html)
behind a new internal `src/native/save_dialog.rs` boundary. The internal API
accepts only an application-owned suggested filename and plain-text extension
filter and returns `Selected(PathBuf)`, `Cancelled`, or `Unavailable`; no `rfd`
type escapes the module. The adapter selects a destination only. It never opens,
writes, truncates, or replaces the selected path, and terminal output cannot
provide the path or filename.

Linux uses the XDG desktop portal backend on both Wayland and X11. macOS uses
the native windowed application dialog, and Windows uses the native Windows
save dialog. Opening the dialog is event-loop asynchronous and cannot stall PTY
processing or the ordinary terminal render/input path. Cancellation and adapter
failure write nothing and return control to the terminal without changing the
selection or command-range state.

Phase C pins `rfd` exactly at 0.17.2 with default features disabled and only
`xdg-portal` enabled. The crate is MIT licensed. In the locked graph it is the
only newly added package; its active Linux dependencies (`libc`, `log`,
`percent-encoding`, `pollster`, and `raw-window-handle`) were already present,
and macOS adds existing Objective-C support edges. The adapter compiles through
the ordinary locked project build; the release gate still requires the pinned
Rust 1.96 CI leg plus independent Linux Wayland, Linux X11, macOS, and Windows
build/test evidence. A failed dependency, license, MSRV, security, or platform
review leaves command export unavailable; it does not authorize a custom
non-native browser or an unreviewed substitute. The separate B24 writer boundary
owns all filesystem security after selection.
