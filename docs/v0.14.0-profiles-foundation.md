# v0.14.0 named profiles foundation

Status: foundation, Profile Manager, launch routing, restoration, and opt-in
auto-switch landed in-tree.

## Schema

Named launch profiles live as one hand-editable JSON document per profile under
`<config-dir>/profiles/<name>.profile.json`. Each file carries:

- `schema_version` (currently `1`)
- launch fields: optional `shell`, `command`, `working_directory`, bounded `env`
- appearance/cursor/effects overrides using the same string vocabulary as
  `odytty.conf`
- optional `connection` alias and `layout.saved_layout` reference
- optional `platforms` applicability list
- preserved unknown keys at every schema-owned object for forward compatibility

Profiles never provide a secret-storage field: secret-shaped keys and
private-key material are rejected recursively across the complete JSON document
at parse time. Writes re-serialize through that same parser, so a
programmatically constructed profile cannot persist secrets or over-limit
fields that a file parse would reject. Profile files are written atomically
with owner-private permissions because launch commands, directories, host
aliases, and environment values remain personal metadata even when they are
not credentials. `schema_version` must be a whole number.

Implementation: `src/profiles/schema.rs`, `src/profiles/store.rs`.

## Settings UI

Settings exposes a **Profiles** section with an **Open Profile Manager** action.
The manager is presentation-only and loads the local catalog when opened:

- create, edit, duplicate, rename, validate, import, export, and delete
- destructive delete requires confirmation
- unknown future keys survive edit/save via the schema round-trip
- import/export use the native file dialog; validation rejects secrets before
  any write
- catalog load never runs on the ordinary default launch path

Implementation: `src/native/profile_manager.rs` plus overlay/settings wiring.

## Precedence

Effective launch resolution follows the v0.13.0 ADR chain extended for v0.14.0
explicit named-profile selection:

1. built-in defaults
2. global config file
3. named profile overrides (when a profile name resolves)
4. workspace named-profile binding (`launch_profile` on workspaces; not the shipped
   `default_profile` connection-host alias)
5. startup environment variables
6. restored hints
7. explicit CLI overrides
8. live UI edits

For settings and for launch fields that expose live/CLI/restored/profile layers
(`working_directory`, `title`), live UI edits win over CLI, restored, and
profile values. Other launch fields (`shell`, `command`, `connection`, `layout`,
`env`) currently merge only CLI and profile layers (CLI wins).

Explicit named-profile selection arrives through CLI `--profile`, restored
`profile_name` hints, workspace `launch_profile`, the command palette, or the
connection manager (`Ctrl+Shift+S`). The shipped workspace `default_profile` field
remains a **connection-host alias** for SSH New Tab routing and is excluded from
the named-profile catalog resolver.

Launch routing loads the local catalog only when a profile is explicitly selected
(new tab/workspace palette, CLI, workspace binding, layout open/restore,
connection manager, or restoration hint). The ordinary default launch path does
not scan profiles or run shell discovery.

Opt-in auto-switch (`profile_auto_switch`, `ODYTTY_PROFILE_AUTO_SWITCH`) evaluates
local `switch.match_hosts` / `switch.match_directories` rules when the focused
pane's working directory changes. Host patterns support exact names, `*`, and
`*suffix` suffix wildcards (for example `*.example`). When the active profile
still matches the context, switching holds steady instead of alternating across
repeated cwd events. Matches apply appearance through the existing session seam
and show a short HUD disclosure; terminal output cannot select or rewrite profiles.
Remote panes use only the trusted saved host identity for host rules.

Shell discovery (`src/profiles/discovery.rs`) is cached and runs only when a UI
surface requests suggestions (Profile Manager / future pickers). Windows lists
PowerShell, cmd, and WSL distributions read-only; macOS/Linux use `/etc/shells`
and common login shells.

Implementation: `src/profiles/precedence.rs`, `src/profiles/launch.rs`,
`src/profiles/switch.rs`, `src/native/app/profile_launch.rs`,
`src/native/app/profile_switch.rs`, `src/native/app/commands.rs`,
`src/native/palette_overlay.rs`.

## Migration and startup

- `profile_from_connection_host` maps legacy host appearance fields into a named
  profile without moving transport fields out of `hosts.conf`.
- `normalize_workspace_connection_binding` trims the shipped `default_profile`
  host-alias string without reinterpreting it as a named profile.
- Local catalog loading scans only `<config-dir>/profiles`; it never executes
  shell discovery, WSL enumeration, or remote checks on the default launch path.
