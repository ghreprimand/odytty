# v0.14.0 named profiles foundation

Status: foundation, Profile Manager, launch routing, restoration, and opt-in
auto-switch landed in-tree.

## Schema

Named launch profiles live as one hand-editable JSON document per profile under
`<config-dir>/profiles/<name>.profile.json`. Each file carries:

- `schema_version` (currently `1`)
- launch fields: optional `shell`, `command`, `working_directory`, bounded `env`
- appearance/cursor/effects overrides using the same string vocabulary as
  `odytty.conf`
- optional `connection` alias and `layout.saved_layout` reference
- optional `platforms` applicability list
- preserved unknown keys at every schema-owned object for forward compatibility

Profiles never provide a secret-storage field: secret-shaped keys and
private-key material are rejected recursively across the complete JSON document
at parse time. Writes re-serialize through that same parser, so a
programmatically constructed profile cannot persist secrets or over-limit
fields that a file parse would reject. Profile files are written atomically
with owner-private permissions because launch commands, directories, host
aliases, and environment values remain personal metadata even when they are
not credentials. `schema_version` must be a whole number.

Implementation: `src/profiles/schema.rs`, `src/profiles/store.rs`.

## Settings UI

Settings exposes a **Profiles** section with an **Open Profile Manager** action.
The manager is presentation-only and loads the local catalog when opened:

- every schema option is editable: shell, command and arguments, bounded
  environment overrides, appearance, cursor, effects, saved layout, local
  switching rules, connection reference, and platform applicability
- command arguments, environment entries, host rules, and directory rules have
  explicit add, edit, and remove rows; the documented schema limits remain
  enforced with an inline message
- boolean overrides cycle inherit/on/off and enumerations cycle only supported
  values; platforms select inherit, Linux, macOS, Windows, or all without
  executing a platform command
- the theme row cycles the sorted built-in roster plus any user theme files with
  Left/Right (typing a name still works); an unknown theme name is rejected at
  save rather than falling back silently at launch
- a starting directory the user sets or changes is checked for existence at
  save; a value loaded unchanged from an existing profile round-trips even if it
  is momentarily missing
- the form and catalog scroll under the mouse wheel without moving focus and
  show a scroll indicator when more rows sit below the view
- press `/` to start the catalog filter; while filtering every printable
  character reaches the query, so the single-key hotkeys never steal a
  character of a profile name

- create, edit, duplicate, rename, validate, import, export, and delete
- destructive delete requires confirmation
- deleting or renaming the global default clears or rewrites the saved
  `default_launch_profile`, and any workspace-scoped override naming the profile
  is cleared or rewritten to match
- unknown future keys survive edit/save via the schema round-trip
- import/export use the native file dialog; validation rejects secrets before
  any write
- catalog load never runs on the ordinary default launch path

Implementation: `src/native/profile_manager.rs` plus overlay/settings wiring.

## Precedence

Effective launch resolution follows the v0.13.0 ADR chain extended for v0.14.0
explicit named-profile selection:

1. built-in defaults
2. global config file
3. named profile overrides (when a profile name resolves)
4. workspace named-profile binding (`launch_profile` on workspaces; not the shipped
   `default_profile` connection-host alias)
5. startup environment variables
6. restored hints
7. explicit CLI overrides
8. live UI edits

Plain **New Tab** and **New Workspace** (the `+` affordance and their keyboard
shortcuts) resolve an effective default profile without opening the chooser:
workspace `launch_profile` when set, otherwise the global `default_launch_profile`
from `odytty.conf` (set via Profile Manager **Set as Default**). Only a configured
name triggers a bounded local catalog read. When neither is configured the launch
is the built-in System Default and the profile directory is not scanned; when the
saved name is missing or invalid, launch falls back to System Default with a
bounded one-line notice and the saved default is left untouched. The first window
follows the same rule: `--profile` wins, then the global default, then System
Default. Host bindings (`default_profile` host alias) still win for New Tab SSH
routing, and explicit host or profile choices open a plain placeholder workspace
rather than layering on the global default.

An adjacent **▾** chevron beside the tab-strip and workspace-rail `+` opens the
lazy-loaded profile picker; context-menu and command-palette routes remain available.

For settings and for launch fields that expose live/CLI/restored/profile layers
(`working_directory`, `title`), live UI edits win over CLI, restored, and
profile values. Other launch fields (`shell`, `command`, `connection`, `layout`,
`env`) currently merge only CLI and profile layers (CLI wins).

Explicit named-profile selection arrives through CLI `--profile`, restored
`profile_name` hints, workspace `launch_profile`, the command palette, or the
connection manager (`Ctrl+Shift+S`). The shipped workspace `default_profile` field
remains a **connection-host alias** for SSH New Tab routing and is excluded from
the named-profile catalog resolver.

Launch routing loads the local catalog only when a profile is selected
(new tab/workspace palette or chooser, CLI, workspace binding, configured global
default, layout open/restore, connection manager, or restoration hint). The
System Default launch path does not scan profiles or run shell discovery.

Opt-in auto-switch (`profile_auto_switch`, `ODYTTY_PROFILE_AUTO_SWITCH`) evaluates
local `switch.match_hosts` / `switch.match_directories` rules when the focused
pane's working directory changes. Host patterns support exact names, `*`, and
`*suffix` suffix wildcards (for example `*.example`). When the active profile
still matches the context, switching holds steady instead of alternating across
repeated cwd events. Matches apply appearance through the existing session seam
and show a short HUD disclosure; terminal output cannot select or rewrite profiles.
Remote panes use only the trusted saved host identity for host rules.

Shell discovery (`src/profiles/discovery.rs`) is cached and runs only when a UI
surface requests suggestions (Profile Manager / future pickers). Windows lists
PowerShell, cmd, and WSL distributions read-only; macOS/Linux use `/etc/shells`
and common login shells.

Implementation: `src/profiles/precedence.rs`, `src/profiles/launch.rs`,
`src/profiles/switch.rs`, `src/native/app/profile_launch.rs`,
`src/native/app/profile_picker_ui.rs`, `src/native/app/profile_switch.rs`,
`src/native/app/commands.rs`, `src/native/palette_overlay.rs`,
`src/native/profile_picker.rs`.

Direct menu routes (v0.14): context menus expose **New Tab with Profile...** and
**New Workspace with Profile...** beside the plain one-click New Tab / New
Workspace rows. Each opens the lazy-loaded profile picker; accepting a row
launches through the same resolver as palette/CLI routes. New Workspace with
Profile creates the workspace, binds `launch_profile`, and spawns its first tab
atomically (SSH connection profiles reuse the connect-in-new-workspace path).

## Launch behavior

A launched profile applies its full context, including the common case of a
profile that customizes only environment or appearance:

- bounded `env` overrides reach the child even when the profile sets no shell or
  command; the default-shell spawn applies them after the standard interactive
  setup so a profile value wins over a discovery advertisement. On Unix they
  pass through fork/exec; on Windows they fold into the ConPTY environment block.
- a resolved starting directory that no longer exists does not fail the tab: the
  spawn falls back to home (`$HOME` on Unix, `%USERPROFILE%` on Windows) with a
  bounded notice, on the new-tab and restore paths alike.
- the theme a profile selects is carried as per-session state. A global theme
  sweep (settings write, OS dark/light flip, restore seed) re-derives each
  session's colors individually and never flattens a profile tab; while a
  profile tab is active the window chrome presents that theme and switches back
  on a tab or workspace switch to a plain pane. Colour-vision adaptation still
  applies on top.

## Migration and startup

- `profile_from_connection_host` maps legacy host appearance fields into a named
  profile without moving transport fields out of `hosts.conf`.
- `normalize_workspace_connection_binding` trims the shipped `default_profile`
  host-alias string without reinterpreting it as a named profile.
- Local catalog loading scans only `<config-dir>/profiles`; it never executes
  shell discovery, WSL enumeration, or remote checks on the default launch path.
