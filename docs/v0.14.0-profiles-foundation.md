# v0.14.0 named profiles foundation

Status: foundation landed in-tree; settings UI, launch routing, and shell
discovery remain follow-on work.

## Schema

Named launch profiles live as one hand-editable JSON document per profile under
`<config-dir>/profiles/<name>.profile.json`. Each file carries:

- `schema_version` (currently `1`)
- launch fields: optional `shell`, `command`, `working_directory`, bounded `env`
- appearance/cursor/effects overrides using the same string vocabulary as
  `odytty.conf`
- optional `connection` alias and `layout.saved_layout` reference
- optional `platforms` applicability list
- preserved unknown keys at every schema-owned object for forward compatibility

Profiles never provide a secret-storage field: secret-shaped keys and
private-key material are rejected recursively across the complete JSON document
at parse time. Writes re-serialize through that same parser, so a
programmatically constructed profile cannot persist secrets or over-limit
fields that a file parse would reject. Profile files are written atomically
with owner-private permissions because launch commands, directories, host
aliases, and environment values remain personal metadata even when they are
not credentials. `schema_version` must be a whole number.

Implementation: `src/profiles/schema.rs`, `src/profiles/store.rs`.

## Precedence

Effective launch resolution follows the v0.13.0 ADR chain extended for v0.14.0
explicit named-profile selection:

1. built-in defaults
2. global config file
3. named profile overrides (when a profile name resolves)
4. workspace named-profile binding (future explicit field; not the shipped
   `default_profile` key)
5. startup environment variables
6. restored hints
7. explicit CLI overrides
8. live UI edits

For settings and for launch fields that expose live/CLI/restored/profile layers
(`working_directory`, `title`), live UI edits win over CLI, restored, and
profile values. Other launch fields (`shell`, `command`, `connection`, `layout`,
`env`) currently merge only CLI and profile layers (CLI wins).

Explicit named-profile selection arrives only through CLI overrides or restored
`profile_name` hints. The shipped workspace `default_profile` field remains a
**connection-host alias** for SSH New Tab routing and is excluded from the
named-profile catalog resolver.

A missing profile warns once and falls back to global settings. Connection-host
Theme/Font/Title fields remain connection data; migration helpers can derive a
named profile without silently aliasing host rows into the general catalog.

Implementation: `src/profiles/precedence.rs`.

## Migration and startup

- `profile_from_connection_host` maps legacy host appearance fields into a named
  profile without moving transport fields out of `hosts.conf`.
- `normalize_workspace_connection_binding` trims the shipped `default_profile`
  host-alias string without reinterpreting it as a named profile.
- Local catalog loading scans only `<config-dir>/profiles`; it never executes
  shell discovery, WSL enumeration, or remote checks on the default launch path.
